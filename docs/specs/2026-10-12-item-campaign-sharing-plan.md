## Goal and boundaries

Allow an author to share one existing active ordinary homebrew item with an exact same-system campaign in which they are a member, and let the author or that campaign's owner revoke that exact access, using the existing campaign-sharing contract. Members discover current shared content through existing type-independent Library permissions; author edits remain owner-only. First share/final unshare create an immutable scope version; intermediate campaign changes preserve version; existing exact inventory/content pins and copy behavior are never rewritten. This child is ordinary content_type=item only.

Do not extend magic_item/weapon/armor/race/trait/feature/monster/NPC/companion, custom types, import rights, public/platform publishing, content packs, character grants, mechanics, copy/lifecycle/R09 readiness or durable operation receipts. Other currently authorable new families have personal-only DALs; companion has no authoring writer. R13 broader search/sort/registry UI and all remaining sharing families stay open.

## Staged SQL contract — no activation by implication

One BEGIN/COMMIT source installation retains exact signatures/return columns/security-definer search_path='' and current owner/grants. Same-transaction REVOKE/GRANT preserves authenticated-only RPC execution, no anon/service-role/public caller grant or new role membership. Existing three types retain original bodies/permissions/results without new validation or behavior; only the allowlist addition affects their enclosing query. Unknown/future types remain refused.

For item only:
- Require active homebrew item with nonnull owner and personal|shared scope, actual published dnd-5e-2014 system. Lock the item current row before expected-version CAS. Require expected_version in1..2147483647. Bind the canonical published system under a compatible row lock in the existing transaction; actual role/lock ordering remains G2 proof. No guessed system or schema defaults.
- Retain exact campaign same-system/owner/member row locks and predicates: only content owner can enable, membership required, content_import_origins membership prohibits enabling irrespective of alleged rights/form values. Revoke retains owner or exact campaign owner authority; an unrelated DM/member has no authority. Former member author can revoke existing shares. No cross-account source access or platform conversion.
- Retain content_id/campaign_id unique insertion/deletion/count and derived scope. Scope stays shared iff count>0. No-op/duplicate share, intermediate addition/removal and unrelated campaigns must not manufacture version changes. First/final scope transition increments exactly one via existing trigger; version exhaustion aborts atomically, including any prior share-row mutation.
- UPDATE changes only scope and captures exact RETURNING content_id/version/scope. For item, immediately after UPDATE and existing AFTER snapshot trigger, validate the exact stored content_versions(content_id, RETURNING version) row INSIDE THIS SAME transaction. Require snapshot scope=derived/written scope and full immutable system/type/source/owner/name/slug/data/effects correspondence to locked item plus scope change; require returned version=old version or old+1 precisely according to whether scope changed. Missing/mismatched snapshot or result raises and rolls back shares/scope/counter/snapshot together.
- Do not verify by later current-row PostgREST read: another edit may have committed. Do not expose raw private snapshot content in RPC return. Campaign-owner final revoke legitimately removes visibility of the new personal snapshot; an external post-read would be wrong and must not motivate read grants.
- Preserve all old character pin bytes/version identities, public/private access helpers and version immutability. No orphaned administrative partial-success handling, snapshot repair or exception swallowing. Actual PG trigger timing/full concurrency/role acceptance is unproved until G2.

## Adapter, action and draft semantics

All item reads/writes require getUser authentication and the existing exact published-system resolver (.single status=published/slug=dnd-5e-2014). Owned item routes cannot be reused to edit another member's shared item. Scope filters become in(personal,shared) only alongside original owner/system/source/type/active constraints and expected version CAS, including conflict relookup. Do not turn a malformed/failed access projection into an empty list.

Sharing adapters validate UUIDs, booleans and bounded PG versions before the single RPC. Parse exactly one returned row (not arbitrary first row), exact requested contentId, bounded returned version compatible with expected or expected+1, scope/count consistency and enable count>=1. Same-transaction SQL proof establishes the written snapshot; a later current catalog version must never replace the returned version.

Sharing has NO operation-ID/immutable command receipt. Typed pre-write permission/input/conflict or transaction-rollback errors are errors/conflicts; transport loss, ambiguous result/malformed success after dispatch is UNCERTAIN, disables further share submits until explicit reload/reconciliation, preserves selected campaign/draft/request, and never automatically retries, fabricates success or claims R09 replay. Return no private response-body details. New share-state uncertainty need not expand existing item-create result types.

Panel owns latest share result version/scope/count and exact campaign selected state; currently ineligible nonshared campaigns cannot enable, existing shares remain removable. State/revalidation must retain prior campaign toggles correctly. Pending duplicate submits are disabled. Sharing concerns the saved definition, not unsaved draft edits. No hidden forms or selectors from another family.

ItemForm binds the initial mounted draft id/version to fields. If server revalidation supplies another version or id while old draft survives, save is refused with explicit reload guidance; it neither swaps hidden expected_version onto dirty fields nor silently resets/remounts them. Normal stale concurrent writes still reach original server CAS when not yet detected locally. Scope first/final transitions therefore cannot authorize overwriting unrelated concurrent content edits. Existing effect omission and private-create semantics stay intact.

Cache invalidation includes exact item edit page, Homebrew, Library, selected campaign settings after a confirmed share. Revoke action uses explicit item branch; settings already renders its returned type/version and exact hidden campaign/content/version. Conflicts/uncertain results do not emit revoked success.
