# Finite enrolled parent admission

This staged companion is a bounded continuation of
`2026-10-22-enrolled-character-writer-fences.md`. It installs after the explicit
Fiend correction and immutable subclass HP companions. It closes unaccepted
mechanical parent UPDATEs and enrolled DELETEs. Child DML/order, catalog/access,
copy/award compatibility beyond the existing builder award, campaign changes,
account/provider/RI lifecycle and general gameplay commands remain open work.
No hosted install, deployment, global readiness or activation is supplied.

Enrollment is an actual `private.character_class_origin_v1` row. A closed,
volatile lookup uses the existing native postgres owner, whose admitted posture
is NOSUPERUSER and BYPASSRLS. It checks that exact owner/visibility posture on
every call and sets row_security=off. Restrictive or changed origin SELECT
policies therefore cannot turn an enrolled row into apparent absence. Owner,
visibility or permission drift raises. The installer also preserves and checks
the existing isolated class-owner role and policy profile for B3 collaborators.
No role attributes, origin grants or policies are changed. The row trigger checks
both OLD and NEW IDs. It never derives
enrollment from choices, caller JSON, a capability, role or a hidden query row.

An unconditional BEFORE STATEMENT trigger acquires the existing singleton writer
guard before direct parent UPDATE/DELETE row locks, including zero-row and
metadata statements. Native builder/B3 entrypoints retain their existing Auth
user/session/profile -> singleton -> parent ordering. Four legacy RPCs lock a
parent before their UPDATE, so their exact source profiles receive a guard call
before that first lock: ability save, conditional state CAS, background selection
and ASI selection. The first two retain SECURITY INVOKER and their original ACLs,
owner, RLS behavior and validation. They call a public NOARG guard-only bridge
owned by the admitted existing guard authority. Its EXEC union comes only from
the actual existing authenticated/service RPC grants plus internal postgres;
anon/PUBLIC and private-schema access remain closed. The bridge only locks and
supplies no actor, plan, mutation or revision authority. The definer background
and ASI RPCs use a closed internal guard wrapper. The simple SQL state-patch RPC
already starts with UPDATE, so the statement trigger supplies its lock edge.

Every admitted physical UPDATE has a closed current-transaction seal containing
its exact OLD and expected mechanical tuples, source and intermediate order.
The tuple includes ID, owner, system, campaign, archive status, level, choices,
state, base scores and database-owned action revision. The sources are fixed
validated compiler/write sites: catalog, progression/acquisition/removal,
details, ordinary ability/equipment/background choices and narrative, the
existing equipment award, and B3's genuine sealed first-class plan/journal proof.
A capability or command name alone supplies no expected tuple or admission.

The early BEFORE trigger sorts before all existing row callbacks. It requires
the exact pending OLD/expected nonrevision NEW and unchanged caller revision,
then marks the seal checked once. The late BEFORE trigger sorts after native
R09 and ASI pruning and requires the exact assigned tuple/revision. The AFTER
trigger sorts after the original callbacks, compares NEW with the stored parent
and checks the intermediate original order with only its producer revision
rebound. R09 alone assigns the revision; its existing first-class, metadata,
ordinary, correction-bridge, exhaustion and caller-revision branches stay
unchanged. Existing finish logic proves the final graph/order before the new
finisher requires observation and consumes the seals.

There are two genuine ordinary parent writes in one existing path: selecting a
background or background choice may subsequently prune invalid Expertise. Each
write has its own pending -> checked -> observed seal and native revision. The
second seal requires the first observation and an exact immediately preceding
OLD tuple, derives its revision from that OLD, and is bounded to sequence two.
The second trusted source site arms only when its existing DISTINCT predicate
will write. Two actual updates retain two increments; no extra no-op UPDATE or
changed accepted behavior is introduced.

The validated unchanged-background return can perform zero parent writes. Its
closed no-write observer rechecks the fresh whole parent, admitted capability,
protected graph, exact existing selected immutable background pin and unchanged
order. Its explicit `write_required=false` proof passes the same internal three
phases without changing the parent/revision. An observed no-write proof can
never admit a later UPDATE. The known Expertise site may still arm the explicit
second physical write, preserving the old zero-or-one increment behavior.

B3 uses the existing actual current-xid pending proof and
`class_first_acquisition_inputs_v1` plan/journal checks. Simultaneous B3 and
ordinary capabilities refuse. The new parent proof observes the actual native
UPDATE; B3's existing observer validates RETURNING, stored tuple and order before
the new parent finisher runs while the original proof is still assigned. B3's
later assigned -> observed/full-graph/deferred finalizer remains unchanged and
mandatory. Parent observation is not full B3 acceptance.

Deferred constraints independently require both new seals and ordinary
capabilities to be absent at transaction end. They reject an early return with
no proof, an unfinished proof, or deletion of a proof while its capability
remains. Failure at any point rolls back parent, native revision/order, phase
changes, graph and receipt together. Metadata-only updates outside an active
capability/proof retain the same mechanical tuple and existing behavior. Every
enrolled DELETE refuses until an explicit lifecycle protocol is reviewed.
