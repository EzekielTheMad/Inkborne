## Approved R06.2 contract freeze (before implementation)

The independent challenge and root compatibility decision approved the following v2 semantics, superseding the open alternatives below. Implementation is bounded to this contract; historical correction/backfill, size/string effects, subrace structured-source expansion, SQL and repinning remain outside it.

- Canonical **optional** race field `ability_score_representation: { version: 1, mode: 'effects' | 'scores' }`. The object rejects unknown members, unsupported versions/modes, null and malformed declarations. No inferred/default declaration is persisted or supplied. `scores` mode requires the actual six-slot canonical scores array; all-zero arrays are valid. `effects` mode allows optional canonical scores as metadata only. Invalid declarations fail canonical parsing and cannot quietly fall back to legacy semantics; runtime source resolution must also reject invalid declarations instead of choosing a mode.
- `effects` mode contributes only original effects; `scores` mode prepends the first race's six-slot additions once and preserves every independent original effect. **Absent declaration** retains existing live behavior: the first race's scores additions plus all raw effects in their existing order. No effect equality matching/deduplication, broad effect suppression, subrace scores addition, snapshot rewrite or automatic repin.
- The new actual race transformer emits original ability effects once, omits the redundant mechanical scores array, and declares version1/effects intent. Existing supplied legacy fixtures keep their original dual representation explicitly; fixture generation must not silently rebuild old pins using the new transformer.
- One pure resolver selects the first structured race's ability contributions. Evaluation applies that list once. All affected Race/Class/Abilities previews and totals receive the same structured sources as page baseline/live provider/durable model. Existing baseline maxHP versus temporary live Constitution, raw HP rolls, class order/rules, CAS/receipt guards, and other source precedence remain unchanged.
- Visible ambiguity means the **first race** has an absent declaration, a canonical scores array and at least one mechanical effect on one of the six canonical ability targets (including conditional/formula effects). Matching values, currently inactive conditions and zero score entries do not prove duplicate intent. Race/Class/Abilities and live sheet show that both representations are retained and their overlapping intent is unspecified; explicit modes and single representations do not display this legacy notice.
- Abilities totals use actual evaluation, not the old blanket scores/effects preference. Source attribution can identify contributing content and state that manual/conditional/formula effects are included according to current evaluation; it must not invent a numeric per-source breakdown or ignore conditions/formulas. Current subrace effects participate as before, but enriched subrace scores remain outside the first-race structured contract.
- SQL remains static-supported-subset only: its existing preference/exclusion, subrace score handling and lack of conditional/formula evaluation can still differ. No SQL edit or server parity claim. Browser/full/build stay held until root resource release; focused tests with two workers, typecheck/lint and exact-source independent review are authorized.

## Recommendation and smallest safe sequence

Do not suppress all race ability effects, prefer scores globally, or match numerical values to erase duplicates. Each fails the manual/conditional/formula controls. Use an **explicit versioned representation contract** at the content source boundary before flattening:

1. New/imported ability bonuses use effects as the sole mechanical representation. The importer can omit redundant scores; every original bonus stays one ordinary effect. If a future product needs a stored scores display array as well, it must additionally carry a canonical, parsed `effects` representation declaration; that array is then metadata, never a second contribution. No marker is needed merely to emit effects-only content.
2. Genuine structured-only records use scores as mechanical additions and retain all independent effects. An explicit `scores` mode makes that intent clear for dual records with manual effects. A versioned mode is a validated owner-editable semantic declaration, **not unforgeable provenance or authorization**. Future authoring must derive it on the authenticated expected-version row and preserve raw data/effects; browser authority flags cannot choose another row or overwrite unrelated metadata.
3. Resolve per-ref representation once from parsed exact version data, then pass one mechanical contribution list to the existing evaluator. Every unchanged raw manual/conditional/formula/grant/narrative effect remains in its original relative order and conditions/state semantics stay in the evaluator. Avoid a second hidden scores prepend. Race preview, Class resolved stats/prerequisites, Abilities totals/sidebar and baseline/live paths must consume this same resolved contract; Abilities must not calculate totals from a separate blanket source-preference sum. Attribution may display source labels without inventing a numeric explanation for formulas.

First implementable product child after challenge: effects-only new importer output plus a small pure source-aware representation resolver and direct consumer wiring, with no alteration to HP rules, race ordering, buffs, source selection or unrelated arithmetic. Canonical enum/validation for explicit dual-mode declaration is a **separate authorized schema contract in that child**, not an unparsed raw marker that current parsers strip. Decide whether to introduce the dual declaration immediately or keep ambiguous dual legacy blocked from adoption; the current checkpoint intentionally does not implement either. Race size/string effects, subrace structured-source participation and general formula timing stay separate defects unless independently brought into scope.

## Historical compatibility and immutability

- Never rewrite `content_versions`, saved pins or original effects. A new importer/catalog version does not replace the race already selected on a character. Parsing a newer version must not mutate or infer an older pin's intent.
- Unmarked **scores-only** and **effects-only** data are mechanically unambiguous and can enter the resolver without deduplication. A scored record containing any additional ability effect is **dual/ambiguous**, even if values match; formula/conditions/manual tags are not evidence of the same grant.
- Unmarked dual historical pins require an explicit compatibility decision. Proposed default: retain current live additive semantics and show the discrepancy/ambiguity; do not silently reduce an existing character's scores/maxHP. Coherent previews would have to show those same retained semantics rather than imply once-only mechanics. This is a compatibility choice, not acceptance that the original imported bonus should be counted twice.
- Fix verified source-generated current definitions only through a reviewed **new content version** that declares effects-only intent. Automatic upgrades are outside this child. If a later request needs corrected arithmetic for an existing immutable pin, it requires a separately reviewed, exact `(system_id, content_id, version, snapshot digest)` compatibility manifest or explicit owner repin workflow. Classification must use reliable import receipts/original source and full raw snapshot review; `source = srd`, slugs, equal numbers, mutable JSON annotations or migration history alone cannot prove intent. No guessed global migration or arbitrary snapshot compatibility map is proposed.
- Race/subrace dependency pinning/entitlements and SQL prerequisite parity remain separate boundaries. The SQL helper cannot represent all conditional/formula semantics, so its supported static prerequisite subset and exclusions must be explicit. No hosted entitlement/persistence claim follows from these component tests.
