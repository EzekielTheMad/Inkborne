## Actual evidence and missing read contract

An ASI-shaped saved choice adds +2 only to Abilities' displayed STR14; evaluated content/sidebar remains STR12. That control supplies saved shape, not earned-grant authorization, and must not become the positive authority fixture.

`AbilitiesStepClient` iterates every `choices.asi_choices` allocation after evaluation, without occurrence validation. Class prerequisites and StatPreview use `evaluate`; `CharacterPage` evaluates content for baseline Constitution/maxHP; `CharacterProvider` adds equipped armor and nonexpired runtime effects for live evaluation; `planHitDieSpend` evaluates baseline/live separately. None synthesizes ASI allocations. Print consumes provider `evalResult`/`maxHp`; it is not another calculator. `buildCharacterStructuredSources` only collects first race/class and feature/feat structured data.

The real write boundary is `setCharacterAsiChoiceRecord` -> `public.set_character_asi_choice`, whose latest captured definition is `20260721224742_restore_feat_choice_rpc_boundary.sql` (not only its older `20260721221108` definition). It locks the owned character, requires exactly one active ASI grant, uses exact immutable feature/controller snapshots, validates one +2 or two distinct +1 allocations, excludes the replaced occurrence for the SQL cap check, and derives feat names/refs. `private.is_character_feature_grant_active` in `20260720185305_character_content_boundary_guards.sql` checks selected class/subclass and earned class level. The frozen grant table and integrity guards are in `20260720173545` / `20260720185127`; duplicate controller/feature entries materialize to one grant with the minimum unlock level. That is existing manifest semantics, not permission to deduplicate arbitrary effects.

`getCharacterContentRefSnapshot` currently selects/parses exact version refs but omits `feature_grant_id`; no application grant-row reader was located. `sync_character_feature_refs` restores refs from captured grants and returns only inserted/deleted counts, not a validated grant manifest DTO. Derived `context` strings and `choice_source` labels alone cannot supply the missing authority. Existing grant SELECT/RLS definitions permit authorized reads statically; effective runtime permissions remain G2. Proposed repair must add a read-only complete grant projection and bind it to the same character/choices/refs used by each consumer. It must not call reconciliation, materialization or a catalog search during calculation.

## Proposed finite contract to challenge before code

First child: **earned, uniquely resolved 5e2014 ASI allocations**, integrated into actual production consumers. Introduce one narrow pure `resolveCharacterAsiContributions` contract returning available contributions with occurrence identities, or explicit unavailable issues; feed that through the existing structured-source/evaluator path, not an unused alternate character model. The authenticated read projection is evidence, not a browser capability. Writers retain their RPC authority and current mutation behavior.

Inputs: character id/system/level and persisted selected class choices; complete immutable content refs with id/character/content id/exact version and derived grant id; complete frozen grant rows including id, character, controller ref/type/slug, feature id/version/slug and unlock level. Feature/controller snapshots pass current canonical parsing. No latest-catalog fallback. Reader must not discard malformed rows and claim completeness. Two reads are not an atomic snapshot: mismatch fails unavailable, refresh/reconciliation returns fresh choices plus the projection, and G2 must test real concurrent mutations. Durable inputs already capture `feature_grants` and refs in their fingerprint; validate their structure with the same resolver rather than trusting their current generic JSON shape.

For each saved occurrence key, require exactly one **active** matching frozen grant and its exact feature snapshot (`feature_type:'asi'`), exactly one selected class/controller pin with matching id/version/system/character/type/slug, and an earned unlock level 1..20 within that selected class's level. Subclass controller must match the selected subclass and its pinned `parent_class`; class/subclass level/identity collisions are unavailable. Require the exact active derived feature ref to agree with the grant, including grant id; missing refs remain a restore/reload problem. Feature levels use the frozen grant unlock level, checking pinned manifest agreement under the existing minimum-unlock materialization rule; do not invent an extra allocation for repeated manifest slug occurrences. Two active grants with the same choice key are ambiguous even when allocations/numbers match. Inactive future grants do not authorize a saved allocation. Removed class/subclass or level-down makes that occurrence unearned without deleting its choice in this child.

ASI allocation shape must be an actual supported object/array: six shipped ability slugs present in the actual 2014 system schema; exactly one amount2 or two distinct amount1; finite integers, no zero/negative/fraction/string/null/unknown target/extra allocation members. Unsupported system/schema, missing projection, duplicate ids, mismatched versions, foreign rows, malformed choices or colliding keys cannot quietly contribute zero as a confirmed total. A clean complete character with no saved ASI choices is a legitimate empty contribution. Historical choices/pins/base scores are never rewritten, normalized, clamped, deduplicated or repinned.

Feat mode synthesizes **no allocation effects**. Existing exact pinned feat effects retain their ref order and normal evaluation, with occurrence-bound feat identity/version and `choice:asi:<grant-id>` checked for the selected occurrence. Missing/mismatched/duplicate feat linkage is unavailable, not grounds to copy current feat effects or discard unrelated raw effects. Independent feat grants outside ASI remain under their existing contract. An ability effect on the ASI feature or another source is independent: keep it even when its value equals a saved allocation; show source attribution without guessed numeric provenance.

**Proposed ordering (requires explicit reviewer agreement):** synthesize ordinary numeric mechanical `add` effects once, in selected-class order, then controller pinned manifest occurrence order (grant identity tie-break only for an otherwise proven unique occurrence), preserving allocation order. Insert after existing first-race structured additions and before original content effects; do not reorder any original effect/ref or alter conditions/formulas. Existing evaluator priority remains set -> add -> min -> max -> multiply, then formulas. This is not Abilities' former post-evaluation addition: base10 + ASI2 + multiply2 becomes24, whereas old Abilities showed22. A formula `strength * 2` similarly sees the ASI and yields24; a final constant formula can override the allocation. These are explicit compatibility changes to challenge and prove, not silent legacy arithmetic cleanup. Source labels identify validated nominal allocations; evaluated totals do not pretend nonlinear effects have separable per-source sums.

**Proposed maximum policy (also challenge before code):** retain the existing save RPC's cap20 and exclusion-of-current-occurrence semantics; do not apply a second read-time clamp or reject temporary live buffs above20. For a previously saved, earned, structurally valid allocation, calculate its contribution even if a later manual/base/content change produces a baseline score above20, with a visible cap-unverified warning; never alter that stored choice/base. Invalid allocation shapes are unavailable instead. `scoresMaximum`/cap-raising feature interpretations and validating historical cap eligibility are unsupported here. Require separate baseline-above20, transient-above20, multiple earned ASIs, and replaced-choice controls. This preserves saved allocation evidence without falsely claiming SQL prerequisite/write-cap equivalence. If challenge requires a stricter historical policy, freeze it explicitly before implementation; do not guess intent from final numbers.

Unavailable ASI evidence must have visible builder/sheet disclosure and unavailable prerequisite/action status. Existing content-only calculations may remain labelled degraded display, never a confirmed ASI-inclusive total; print and dependent durable/roll/relative-HP operations refuse unavailable mechanics rather than persist guessed values. Preserve old unverified Abilities allocation evidence in a separately labelled saved-choice disclosure, not a hidden live bonus or silent deletion. Exact degraded UI/action scope and cap-warning behavior need approval because this changes the former raw-only display contract. Raw scores-only subrace compatibility/R06.4 stays separately labelled and unexpanded.

Abilities removes its second applied bonus, retaining nominal allocation labels/disclosures. Class uses persisted confirmed selections for authority; optimistic choices/new levels cannot make an unconfirmed ASI live. After confirmed save or level/subclass/ref changes, use refreshed canonical choices/refs/grants together; stale evidence disables dependent calculations. No new generic calculation architecture or ASI write API.

Provider consumes already shared sources; existing live runtime/equipment effects remain later inputs. Baseline maxHP includes permanent validated ASI Constitution, excludes runtime temporary Constitution as today. Class order, hit dice, campaign HP rule, raw die rolls, current HP/spent values, CAS/dependency/receipt guards remain unchanged. Print uses the same provider result and propagates unavailable mechanics; only disclosure/guard plumbing is necessary there. R06 race representation, raw conditions/formulas, feat effects and effect/ref ordering remain untouched. Inventory, source migrations, ASI storage, SQL and general subrace/size rules are outside the child.
