## Schema, privilege and lifetime contract

Add `characters.action_revision bigint NOT NULL DEFAULT 0 CHECK >= 0`. Browser/service DTO revision is a canonical decimal string; do not cast through JavaScript Number. New kernel increments once; future participating triggers/adapters may increment more than once, so consumers require monotonic advance, not universally `+1`. Maximum refuses before mutation. Existing writers remain unfenced and therefore kernel enablement remains forbidden.

Private `character_action_receipts` has primary key `(character_id, operation_id)` and character FK with authorized character deletion cascade. Columns: contract/canonical versions; canonical intent **text** and intent JSON; dependency fingerprint; complete parsed dependency JSON; verified actor UUID recorded without profile-deletion cascade; before/after revision; accepted full RollResult; exact bounded state delta; linked roll UUID; evaluation instant, accepted native timestamp and expiry deadline. No raw credentials or private narrative fields. Actor deletion alone never removes a surviving character's receipt. Retention is character lifetime, without retry TTL.

Add nullable `character_rolls.action_operation_id`; composite character/operation FK to receipt and partial unique `(character_id, action_operation_id)` for non-null values. Receipt stores the linked roll ID and a deferred cross-check assures matching character/operation/ID and exactly one linked roll at commit. Normal owner inserts must have operation ID NULL; no browser can forge a link. Ordinary unlinked rolls preserve existing behavior.

Receipt UPDATE always denied. Receipt DELETE denied while its parent character exists. Linked roll UPDATE/DELETE likewise denied while parent exists; deletion through authorized character deletion must be characterized explicitly. This protects against the existing profile cascade instead of silently losing a linked roll. It can cause profile deletion to fail safely when a surviving character has that actor's linked roll; **profile-deletion/character-transfer lifecycle compatibility is an enablement prerequisite**, not accepted behavior. Do not silently alter the existing profile FK or ordinary roll retention in this child. PostgreSQL cascade order and target lifecycle tests must prove valid character deletion can complete without orphaning links; otherwise keep command unavailable and redesign retention separately.

All new private tables enable RLS as defense in depth, with no browser/table policies/grants. `PUBLIC`, `anon`, `authenticated`, and `service_role` get no direct receipt/gate DML. ## Canonical serialization compatibility

Reuse exact `canonicalHitDieJson`, `serializeHitDieIntent`, `HIT_DIE_CANONICAL_VERSION = 1`, and strict schema parsing. Request operation ID is the separate lookup key; canonical intent binds character, command, class, expected revision, fingerprint and versions. Same ID plus different exact canonical intent conflicts even if its requested class later disappears. No opportunistic contract-version migration on replay.

Do **not** SHA-256 `jsonb::text` and equate that with JavaScript canonical bytes: whitespace, number rendering, Unicode/key ordering differ. Trusted TypeScript computes fingerprint from the validated DTO. SQL validates the supplied canonical text decodes to exactly the intent object derived from strict request fields, retains the exact text, and compares it byte-for-byte on replay. SQL compares its future reconstructed parsed-shape snapshot with `p_snapshot` using JSONB structural equality, retaining array order and distinguishing missing/null fields. Candidate/request fingerprint equality is required. This is a complete structural freshness fence; it does not turn a caller hash into database authority. Cross-language golden vectors are mandatory before any real adapter.

Future reader must map `characters.user_id` to `owner_id`, revision to text, immutable version snapshots to resolved definitions, and all source arrays through the same validated-shape projection used for fingerprinting. It must preserve raw extension/effect fields that the current schema retains and must not silently strip rows/unknown mechanics. Raw source values that cannot round-trip the strict JSON/number/schema contract reject. No requirement that SQL regenerate canonical JavaScript JSON strings for snapshots.

### Conservative timestamp profile

The current candidate `instantSchema` accepts exactly three fractional digits, while PostgreSQL timestamptz has microsecond precision and active-effect `expires_at` accepts broader ISO text. Freeze a deliberately narrow first-command profile: every non-null effect expiry in the complete active-effect array must already be canonical UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, with a supported year 0001–9999, valid finite Gregorian instant, and an exact native millisecond boundary. Reject finer fractional values, noncanonical offsets/formatting, unsupported dates, infinity and ambiguous/unparseable values before planning and again under commit locks. Even an already-expired effect with an unsupported expiry rejects this first profile; do not silently drop it. Do not round or rewrite stored expiry text/state, and do not route raw microsecond PostgreSQL strings through Date.parse as if it retained precision.

Resolve records the native evaluation `clock_timestamp()` and, **only after all relevant expiry boundaries pass that profile**, floors evaluation to the preceding millisecond with native `date_trunc('milliseconds', instant)` for the canonical three-digit DTO value. With millisecond-exact boundaries, expiry classification at native evaluation and its floor is identical: a boundary at the floor is already expired; the next boundary is at least the following millisecond. Native evaluation is retained separately in the service envelope/audit receipt; it is not inserted into precision-3 planner fields. Formatting must be explicitly UTC with three digits and round-trip checked; no implicit session timezone formatting.

Commit receives the separately retained resolve instant as service-only `p_native_evaluated_at`, validates that its native millisecond floor equals candidate `evaluated_at`, and retains unrounded native `clock_timestamp()` acceptance and native reconstructed expiry deadline. The candidate `evaluated_at`, `rolled_at` and `valid_until` remain canonical millisecond strings; supplied candidate acceptance-check time is only planner evidence. Native comparison is `accepted_at < deadline`, never a floored Date.parse comparison. Native evaluation/acceptance must not move backward; unsupported/future or mismatched projected instants reject. This trusted native input still does not prove a historical resolve happened without a persisted/signed token. No expiry means native/candidate deadline null. Receipt replay bypasses today's precision profile and preserves the original accepted result.

Required submillisecond golden cases: evaluation at `.000999` projects to `.000`, an exact `.001` expiry stays active at planning; native acceptance `.000999` passes, `.001000` and `.001001` reject against that expiry. An expiry `.001001` rejects the unsupported profile without rounding; a six-digit `.001000` textual expiry also rejects the narrow format without rewriting it. Include evaluation/expiry equality, UTC day rollover, no expiry, invalid/offset/year cases, and negative-epoch millisecond-floor behavior. These tests characterize the conservative profile; actual native PG timestamp/formatting tests remain G2 prerequisites.

## Transaction order and checks

1. Strict request/intent bounds and version validation. Lock target character `FOR UPDATE`; recheck current `user_id = p_actor_id`. Missing/foreign reveal no receipt/state. Parent locking serializes concurrent same/different operation IDs for this character. Candidate/snapshot validation is deferred until after receipt lookup, so replay never depends on a fresh candidate.
2. Read existing receipt under parent lock. Matching canonical intent returns stored accepted roll/receipt even when gate off, character archived, current revision changed, inputs removed or expiry passed. A different intent returns operation conflict. Recovery never applies stored old resulting state over current state.
3. For absence only, validate candidate/snapshot envelope; require gate true, not archived, revision equal to strict request and below maximum. Invoke unavailable reader; future body acquires all required locks and reconstructs complete current DTO. Compare identity, ownership, full parsed snapshot and request revision. No lock from an earlier resolve request survives here.
4. Validate saved selected-class pool and die, explicit valid HP/spent/death saves, trusted finite integral Constitution/max HP, one die face in range, matching request/expression/meta/groups/kept/modifier/total, and exact pure planner result. Before **any write or INT4 cast**, require accepted roll total to be an integral numeric value within the existing `character_rolls.total` range **[-2147483648, 2147483647]**. Compute face-plus-modifier and range comparisons using wide numeric/safe-integer arithmetic, never overflowing INT4 intermediates; boundary-plus/minus-one and nonintegral values reject as invalid without receipt/state/roll residue. Do not clamp the accepted roll total or change the existing column type. SQL independently computes the permitted patch from current state plus trusted derived max HP/Constitution: one selected spent count increment, all other spent entries preserved, healing `max(0,total)` clamped to max HP, death-save reset only from zero HP to positive. Never trust arbitrary candidate patch/state wholesale. Derived evaluator values are trusted service computation on the structurally matched snapshot, not a reimplementation of the TypeScript rules in SQL.
5. Obtain `clock_timestamp()` **after locks**, compare native expiry immediately before acceptance (at deadline rejects), following the conservative timestamp profile above. The trusted adapter supplies the millisecond floor of the separately retained earlier native resolve instant to the planner, but without a persisted/signed resolve token SQL cannot independently prove that historical instant originated in that earlier request; do not claim it can. SQL reconstructs relevant native expiries from the locked current snapshot, validates the narrow profile again, derives the first expiry after the supplied supported evaluation instant, compares candidate deadline to that native value, and refuses if native acceptance reaches it. The planner's `acceptance_checked_at` is evidence only. Keep native evaluation/acceptance and deadline in the receipt.
6. Insert immutable receipt; update only allowed state keys and revision, preserve unknown/unrelated current state; insert exactly one linked existing-format roll; deferred link integrity check; return `committed` receipt. All writes are one transaction. Fault/constraint failure anywhere raises and rolls back; never catch after mutation and return an ordinary rejected status. No partial-result fallback.

Operation responses: `committed`, `replayed`, `operation_conflict`, `revision_conflict`, `invalid`, `expired`, `unavailable`, `disabled`, `inaccessible`; lookup adds `absent`. Only authenticated owned transactional rejection with no existing receipt is known non-commit. Receipt-read inaccessible/absent and transport failures retain unresolved operation. Later browser recovery stores full validated request before dispatch in account-scoped sessionStorage; same ID/request only, clears on sign-out/account change for privacy, no assumption that clearing cancels an in-flight transaction. Recovery UI/storage belongs to a later child.
