## First child controls and exact scope

Use ordinary labelled controls, no JSON/effects/relation/authority input. Name and description are required, trimmed, at most 100 and 20,000 characters respectively, matching adjacent authoring bounds. These are authored-subset limits, not new schema constraints. Existing over-bound text cannot be silently truncated.

Primary uses is optional decimal integer text, accepted only by digit syntax plus `Number.isSafeInteger`, range 0 through `Number.MAX_SAFE_INTEGER`. Reject negative, fraction, hex, exponent, NaN, Infinity, unsafe integer, File input and malformed/repeated scalar values. Blank is **unspecified** (omit usages); zero is explicit stored zero (no counter). Safe integer string roundtrip is required. Recovery choices are None, Short rest, Long rest, mapped to null and the exact two shipped strings. Positive uses requires short/long recovery; blank uses requires None. Zero may retain None/short/long as dormant metadata; the form states that zero creates no primary counter. No dawn/day authoring promise in this child.

Resource controls are editable only when the authenticated expected-version raw row has no primary resource (`usages` absent, recovery absent/null), or a safe nonnegative scalar in the supported subset with coherent recovery (positive requires short/long; zero may be null/short/long). Existing 20-slot arrays, dawn/day, fractional/negative/unsafe values or incoherent pairs remain **read-only together** with an accurate explanation; name/description can still be edited when canonical known data is valid. Array/per-level uses, extra limited features, effects, relation arrays and any schema extensions remain retained and unedited. Server computes eligibility from its scoped row; forged `resourceEditable`, usages/recovery or raw extra payloads cannot unlock or overwrite read-only fields. A future resource child can add actual array controls and accurate clock support after separate review.

Create: validate finite controls using the canonical trait schema; server derives `content_type=trait`, system, owner, source/scope, unique generated slug, initial version via existing trigger. Store canonical description, primary resource fields, empty `races`/`subraces`/`extraLimitedFeatures`, and `effects:[]`. Description is already consumed from data by Features; no invented grant or duplicate narrative effect is generated. No new character/ref write.

Edit: retain original internal raw data object and raw effect array, overlay only name/description and eligible **changed** primary resource controls. Before overlay, compare the submitted semantic pair with the controls derived from the authenticated raw row: absent usages maps to blank, zero remains zero; absent or explicit-null recovery maps to None. If the pair is unchanged, do not touch either raw key. Thus a description-only save preserves absent usages/recovery versus explicit zero/null even when canonical parsing supplies defaults. If the pair changes, overlay only semantically changed fields: an explicit usages clear removes that key; a recovery change to None stores null; an unchanged None preserves its original absence/null. This comparison is not authorization and never unlocks a read-only pair. Validate known canonical fields but **persist the merged raw object, not stripped parser output**. UPDATE omits `effects` entirely. Preserve raw unknown nested metadata, relation arrays, extra counters, all effect entries/order/conditions/formulas/extension keys, slug/envelope and existing character pins. Existing narrative effect text may differ from the newly edited data description because its intent is unverifiable; metadata editor must disclose that existing effects and links are retained, with no narrative/mechanics synchronization claim. Raw extensions remain server internal, never exposed as generic editable JSON.

Player-facing disclosure: “This saves a private standalone trait. It does not attach the trait to a race or apply it to a character. Existing links and effects are retained when editing.” Locked resource summary uses player-facing wording (per-level uses or unsupported recovery), not parser/source implementation details. Existing dawn/day summary accurately says counters currently recover on long rest.

## Persistence, version and draft invariants

- `auth.getUser()` before writes and owner-scoped reads; no browser owner/system/source/scope authority. Resolve `dnd-5e-2014` **published** system with `.single()`; missing/duplicate/unpublished system fails without a write.
- List/get/pre-read/update/conflict lookup preserve exact owner, system, `trait`, `homebrew`, `personal`, `is_retired=false`; ID validated UUID and expected version integer **1..2,147,483,647**, matching PostgreSQL integer storage (not the usages safe-integer bound). Action input, row envelope and CAS identity retain this bound; malformed or out-of-range version makes no query/write. Pre-read and single UPDATE use expected-version equality. UPDATE may change only name/data; no scope/source/type/owner/version/slug/retirement mutation.
- Missing initial expected-version row or zero CAS result gets a constrained same-envelope reread: visible newer owner row => conflict, otherwise generic not-found/error. No automatic retry, second overwrite or foreign-row disclosure.
- Form follows shipped native draft retention/reset pattern for validation/transport/CAS failure, with usable field errors and explicit reload/discard behavior. Reload obtains latest scoped row and recomputes locked controls; it is a user action, not an automatic overwrite. Navigation success only after confirmed save.
- Changing a definition is a new catalog version; old snapshot and existing ref ID/version are unchanged. No `content_versions`/`character_content_refs`/`characters`/provider writes, hidden dependency normalization, automatic migration/backfill or share extension.

### Creation uncertainty: concrete action/form behavior

Generated row IDs/slugs identify separate creations; they **do not prevent repeated creates**. This child adds no idempotency receipt, exactly-once guarantee, server authorization token or guessed lookup-by-name success. A pending guard prevents overlapping clicks in this form only. A row may already have been inserted if its response is missing, malformed or lost.

Trait action/form state is a local result union: `idle`, `error` (including field errors), `conflict` for edit CAS, `uncertain`, or `saved` with a validated record ID. Authentication/context/input failures before INSERT return error without a write. Once CREATE is attempted, a missing row, malformed envelope/data, wrong owner/system/type/source/scope/active/version, or transport exception without a confirmed valid row returns uncertain; a database rejection may be called error only when its returned contract proves the write was rejected. A saved state requires the actual returned row to validate against authenticated context and submitted authored fields, UUID and initial PostgreSQL version contract. No success is synthesized from request fields or a generated identifier.

To handle a response lost after the server saved, CREATE returns the validated saved state rather than issuing a server redirect before the browser receives it. The trait form's local action wrapper catches rejected/missing/malformed responses, produces uncertain and keeps all controlled field values. The native reset-prevention/draft preservation path applies to error/conflict/uncertain, including React's post-submit reset. Only a confirmed saved response permits navigation to `/homebrew?created=<validated-id>`; uncertainty performs no success redirect, no draft clearing and no automatic retry. These result states govern feedback/navigation, not write authorization.

Uncertain state displays an alert: “The save could not be confirmed. Your draft is kept. Check your private Homebrew traits before creating again; the trait may already have saved.” Show a normal **Check Homebrew** link. Keep Create disabled until the user deliberately chooses **I checked Homebrew; allow another create**; retain the uncertainty notice and warn that another submit may create a separate trait. That acknowledgement only releases the local form guard and cannot prove absence or authorize anything server-side. An explicit subsequent submit reruns all server validation/authentication and is a new attempt, never an automatic resubmission. No uniqueness/exactly-once claim based on generated IDs, name matching, acknowledgement or an owned-list read. Any navigation away can lose a page-local draft; do not promise durable cross-navigation draft storage in this child.
