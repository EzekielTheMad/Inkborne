## B. Minimal durable starting-equipment operation

This refines the [earlier proposal](2026-10-02-equipment-atomicity-proposal.md). Existing parser, selection completeness, immutable item versions and copy/no-reaward semantics remain authoritative. No starting-gold alternative, respec, second award, creation deduplication or universal action framework is added.

**Contract:** the natural operation key is `(character_id, starting_equipment)`, not a browser request UUID. Canonical intent consists of saved selection/pick maps, pinned class/background versions and the exact validated item/currency plan. Equivalent retries return the original receipt, even after inventory consumption/deletion or currency spending. Different intent after an award returns already-awarded conflict. Transaction failure returns no committed award; a lost response requires receipt lookup/replay, never inferred completion from inventory names or present currency.

**Minimum proposed schema, not applied:** `public.character_starting_grants` (UUID primary key, character FK with delete cascade, fixed grant kind, lifecycle status, nullable canonical intent/receipt until completion, timestamps) as one grant ledger with unique character/grant-kind key, canonical intent, immutable receipt (created inventory IDs, currency delta, timestamp), and lifecycle `eligible` (no committed receipt), `awarded` or `inherited_completion`; nullable `character_inventory.starting_grant_id` FK for grant provenance on inventory rows. Owner-only receipt reads, trusted-server-only ledger writes/function execution; revoke default PUBLIC/anon/authenticated execution on the internal function. No changes to the old state endpoint's permissions are part of this request. No automatic legacy receipt backfill.

**Eligibility initialization:** the new trusted character-creation transaction inserts an `eligible` ledger marker with the new character. Copy initializes eligibility only from an eligible, proven never-awarded source; completed copies initialize `inherited_completion`. No marker means legacy/unverified, not implicit permission to award. This uses the same ledger, not a second eligibility table; the create/copy changes belong in the exact approval scope. An eligible marker is not a success receipt and cannot resolve an ambiguous award as committed.

**Server and transaction:** proposed `public.commit_starting_equipment` is a restricted `SECURITY INVOKER` internal function, with qualified relation names and explicit trusted actor/character ownership checks; its arguments are the server-derived actor, target, expected choices/ref snapshot and validated canonical plan, never a directly callable browser award API. The authenticated server entry derives the user through `getUser`, independently loads accessible pinned sources/selections, and builds the plan through existing parser/completeness rules. Never trust browser owner, inventory award or gold amounts. One restricted internal transaction locks the character, verifies owner and source/selection snapshot, rechecks content-version access, then returns a matching terminal durable receipt, rejects different/completed or absent eligibility, or consumes the eligible marker exactly once. In one commit it finalizes the eligible ledger and inserts pinned/custom inventory, adds currency to current locked amounts, merges only starting-equipment confirmation into current choices, and finalizes the receipt. Failure at any stage rolls all writes back. Exact ordering must permit equivalent receipt replay without requiring the current altered inventory/currency/source catalog to reconstruct the old award; authorize the actor first, then resolve the stored intent/receipt.

A global action revision is **not required for this standalone grant contract**. Relevant pin/ref mutations must share the character lock (review existing boundaries; add only the necessary guard in a separately approved migration) and the transaction compares their current canonical snapshot. Character choices/state updates already contend on the character row, but direct stale replacements can still overwrite later: coordinated writer handling is a separate scope, not silently fixed by this proposal. The function is not a guarantee against arbitrary privileged/direct inventory inserts. Rollout must prevent the old UI's sequential grant path from being used for eligible characters; older/direct clients remain an explicit acceptance limitation unless separately fenced.

**Copy:** retain the existing transaction's choices, state, pinned refs and current inventory copying. A completed source yields a target terminal `inherited_completion` marker and copied-row provenance mapped to target IDs; it adds **zero** award currency/items beyond the ordinary copy. Do not copy an awarded receipt's source inventory IDs as target inventory IDs or present inherited status as a new award. A legacy confirmed string/structured completion without a ledger remains completed/no-reaward and may receive an explicitly labeled inherited marker during copy, not a fabricated historical award receipt. Unconfirmed sources keep unconfirmed selections and copied current inventory; proven never-awarded sources retain the ordinary first-confirmation behavior. Suspected partial legacy sources remain unresolved, not silently blessed or regranted.

**Eligibility and legacy cases:** fresh characters created through the new grant path can establish never-awarded provenance. Existing confirmed characters are read-only/no-reaward even without receipts. Existing unconfirmed characters with possible old partial grants are excluded from automatic grant/reconciliation pending an explicit audited policy; inventory absence alone is not proof because items may have been consumed. Do not change their saved flags, remove items or reset status automatically. This leaves the known legacy-policy question outstanding instead of inventing behavior.

**Local evidence versus durable proof:** existing pure parser and actual equipment/copy caller tests can specify canonical plan inputs, completeness, current copy fidelity and read-only confirmed behavior without network access. A new in-memory ledger test would only restate a hypothetical algorithm and cannot establish PostgreSQL lock, rollback, permissions or durable replay. Do not report such a model as implemented idempotency. After schema implementation is separately approved, require local database integration tests (if an existing authorized runtime is available) and bounded hosted acceptance: failures after ledger/items/currency/confirmation/receipt, simultaneous different request IDs, lost committed response, changed intent, stale pins/access, foreign actor, replay after consumption, confirmed legacy and copy no-reaward. This package contains no SQL migration or production endpoint implementation.

**Implementation approval requested separately from A:** the exact ledger/provenance DDL, internal function grants, owner receipt-read policy, authenticated server entry, trusted creation-transaction eligibility initialization, equipment caller switch, generated types and copy-function eligibility/marker/provenance mapping, plus pin-lock guard only where needed. Verify existing trusted-server capability without credential changes. Hosted migration/test scope must name a disposable staging target and exact fixtures; the one-character state-only allowance in A cannot be repurposed for this. No legacy-endpoint grant changes or production deployment included.

**Rollback:** before deployment, replay forward/down migrations against a disposable approved database and fingerprint existing endpoint/RLS behavior. If no award has committed, disable the new entry and reverse only additive unused objects. After any award or copied completion exists, preserve ledger/provenance/receipts; disable new grants and retain read/replay recovery. Never drop evidence, delete granted real inventory, subtract spent currency or fall back to the sequential old grant path. Copy safety must remain enabled or copying pauses. Removing schema with live receipts requires a separately reviewed data-preserving migration. Transaction failures themselves roll back; application downgrade after committed awards is not a safe semantic rollback.
