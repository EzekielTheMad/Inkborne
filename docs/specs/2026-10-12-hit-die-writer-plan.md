## Actual calculation and dependency boundary

`CharacterProvider.spendHitDie` (`lib/character/character-context.tsx:709`) checks the class pool and non-full HP, computes Constitution from its live evaluator, calls `roll()` inside `createStateWriter.runAction`, then persists `spendHitDiePatch`. `recordRoll` at :630 / `lib/supabase/rolls.ts:14` inserts an independent roll. `lib/sheet/update-state.ts:23` supplies raw-state CAS only for guarded writes; there is no persisted operation identity or monotonic gameplay revision.

Reuse `computeHitDicePools`, `buildHitDieRollRequest`, `spendHitDiePatch` (`lib/hit-dice/helpers.ts`), `evaluate` (`lib/engine/evaluator.ts`), `buildCharacterStructuredSources` (`lib/character/structured-sources.ts:12`), `generateArmorEffects`, `collectActiveEffects`, and `computeMaxHp` (`lib/character/max-hp.ts`). Reconstruct from complete immutable pins, never the current catalog or browser-supplied totals. `getContentRefsByCharacter` (`lib/supabase/content-refs.ts:81`) already has `requireCompleteSnapshots`/`fresh` options; the action must fail on unreadable, duplicate/ambiguous, mismatched, or missing required pins rather than use the helpers' missing-class d8 fallback.

Two existing semantics need explicit root challenge, not a silent rules change:

- Provider :356–415 evaluates equipped armor, equipment-derived state and runtime active effects for roll Constitution. Page `app/(app)/characters/[id]/page.tsx:257–278` computes the **maxHp prop separately from baseline pin effects**, omitting those runtime effects. Preserve that split initially, with parity tests; recomputing max HP from live Constitution would be a separate behavior change.
- The page uses system `schema_definition.hp_rule`; builder `class-step-client.tsx:168` resolves campaign override first. Record both rows in freshness, preserve the page's current rule initially, and leave this mismatch explicitly tracked. Array order matters for primary class and effect precedence. Unordered ref reads must acquire a documented stable order shared with the evaluator; do not sort mechanically significant arrays arbitrarily. Tie-priority effect parity is an acceptance gate.

Snapshot includes character identity/owner/system/campaign/archived status, raw state, base stats/level/choices (classes, HP history, ASI/resolved choices), complete refs and feature/spell grant projections, inventory/custom data and equipped status, schema/expression rules, runtime effects, and relevant source/access rows. Spells do not independently modify Constitution today; include their mutations conservatively because feature reconciliation and casts update mechanical inputs. Narrative/timeline/portrait/color and ordinary manual display rolls are independent unless they replace a mechanical object.

Time is also a dependency: `collectActiveEffects/isExpired` (`lib/active-effects/helpers.ts:139/66`) drops effects at `expires_at` without a database mutation. Resolve must supply a database evaluation instant and the next relevant expiry as a validity deadline; commit rejects a candidate whose active-effect set can have changed by acceptance time. A revision/state hash alone cannot close this race. Preserve receipt-first replay even after that deadline expires.

## Minimal additive API and staged transaction

Suggested reviewed source files: `supabase/staged/hit-die-transaction.sql` (never automatically applied/generated), `lib/character/hit-die-plan.ts` (pure model/canonicalization/evaluation), `lib/supabase/hit-die-server.ts` (`server-only`), a scoped hit-die server action, and an account-scoped recovery module. Update generated database types only for the reviewed staged contract; do not imply the live schema matches them.

- `characters.action_revision bigint NOT NULL DEFAULT 0 CHECK >=0`, database controlled. Advance once or more monotonically for each committed relevant mutation; nested grant/ref effects may advance more than once, never require “+1” globally. No-op writes leave it unchanged. Add a database-owned capability/gate default false; browser flags/headers/GUCs cannot authorize mechanical writes.
- `character_action_receipts`: PK `(character_id, operation_id)`, FK to character; canonical intent JSON/hash + canonicalization/rules contract versions, verified actor, dependency snapshot/hash, accepted full RollResult and state delta, before/after revision, commit time. Immutable UPDATE/DELETE protection and no caller INSERT/UPDATE/DELETE. Character deletion owns retention cleanup; actor/profile deletion alone must not cascade-delete receipts while character survives.
- Nullable `character_rolls.action_operation_id` with composite receipt FK and partial unique `(character_id, action_operation_id)`. Receipt/state/linked roll must all commit or roll back; normal owner insertion policy permits only NULL operation ID.
- Request: character UUID, operation UUID, `spend_hit_die`, chosen class slug, **decimal-string** expected bigint revision, dependency fingerprint and contract version. No actor, HP patch, max HP, Constitution, die face, or result from browser. Bind identity to character/command/class/revision/fingerprint/contract; same ID with different intent conflicts. Canonical object keys ignore order; semantic arrays preserve order.
- Responses distinguish committed/replayed, known rejected conflict/invalid/inaccessible/disabled, and transport uncertainty. Authenticated current-owner lookup precedes any receipt disclosure. An identical receipt returns its original result **before** checking today's revision/pools/pins/rules; refresh current state separately and never apply old receipt state over newer state.

An inaccessible receipt lookup during recovery does not establish that the original request never committed; retain unresolved recovery unless the account privacy policy clears storage. Only a confirmed transactional rejection of an owned, not-previously-committed intent is terminal. Do not turn a lookup denial or empty receipt read into permission to create another operation ID.

Server session `getUser()` verifies the actor. Follow the existing server-only equipment client separation (`lib/supabase/starting-equipment-server.ts`) for a narrowly granted internal commit RPC: caller-supplied actor in that RPC is permitted only from trusted server role, and SQL still checks current ownership. Prefer invoker execution where effective privileges suffice; any definer must have empty search_path, explicit row authorization and revoked PUBLIC/anon/authenticated execute. Do not expose service credentials or accept a browser trust flag.

Because the existing evaluator is TypeScript, use **snapshot/plan → trusted compute → one atomic commit RPC**. The resolver returns one coherent, authorized locked snapshot, including the database time/deadline, from a primary-bound RPC. Each PostgREST call is its own transaction: a resolve lock does not survive to commit. Commit must lock and reconstruct/compare the complete revision/dependency payload itself. Recovery lookup also uses the primary with current-owner serialization; replica lag is not receipt absence. Server candidate RNG uses `node:crypto.randomInt` for an unbiased integer die and injected `executeRoll` (`lib/dice/roller.ts:24`) for the existing breakdown; its default Math.random is not the accepted authority. Candidate RNG is not displayed or logged before acceptance. Replayed/concurrent candidates are discarded in favor of the stored receipt. No sequential state-save + roll-insert fallback.

Commit order: lock current-owned character; compare existing receipt intent and replay if present; validate gate/revision; lock participating dependencies and recheck full canonical snapshot/access; validate strict class/pool/finite derived values; compute/check permitted hit-die delta (one spent die, floor healing at zero, max-HP clamp, reset death saves only when healing zero HP above zero); insert receipt, update state/revision, insert linked roll, return receipt. These are one VOLATILE POST RPC transaction. Do not return a rejected result after partially mutating; exceptions/faults roll back all three writes.

## Fence, lock order, and unresolved implementation decisions

The recommended final fence is explicit **column/table privilege removal**, not an untrusted session marker: remove broad table UPDATE before regranting reviewed nonmechanical character columns, and remove unversioned child DML from browser roles. Revoking a column alone cannot override an existing table-level grant. Legacy invoker state RPCs then cannot write mechanically; existing definer builder/copy/award/member RPCs require audited version-aware adapters or old-signature denial. Service-role generic mechanical writes must also be restricted or replaced; superuser/admin schema authority is an operational trust boundary, not something this API can secure against. A revision trigger alone does not fence stale absolute writes.

Do **not** apply global privilege removals while the old clients still depend on them. Stage the full fence diff now; additive schema/API can remain disabled. Activate the fence only after every listed adapter is accepted. If phased per-character adoption is required, it needs a separately reviewed protected trigger/role authorization design; do not claim the global privilege plan is cohort-scoped.

Proposed global order for reviewed writers: affected character IDs sorted; then shared rows in documented table/ID order (`content_definitions`, `game_systems`, `campaigns`, `campaign_members`, `content_shares`, `content_versions`); then refs/grants/inventory/spells/receipts by stable keys. Use SHARE where immutable-looking non-key inputs must remain unchanged through acceptance, UPDATE for mutations. All writers must use the same order before DML. Direct child UPDATE/DELETE + a parent-locking row trigger does **not** establish parent-first ordering; direct parent deletion/FK cascades have the converse hazard. No SKIP LOCKED for eligibility/receipt acceptance. Missing membership/share insert/delete requires a parent guard or equivalent reviewed phantom protection.

Existing pin read policy (`20260720173545_content_version_policy_performance.sql:351`) deliberately permits referenced-version continuity after sharing revocation, while `private.can_use_content_version` and grant/copy helpers enforce fresh eligibility for new pins. **Recommended first hit-die contract preserves already-pinned continuity**; withdrawal of a campaign share must not silently erase a character's historical mechanics. New pin/grant materialization still requires current eligibility. Root must challenge which shared rows are actual first-command dependencies versus only adapter dependencies; do not expand this into a new revocation policy. Effective target PG/PostgREST version, ACLs, trigger order, shared-row phantom protocol, effect-order parity and final lock compatibility are unresolved acceptance evidence, not hidden assumptions.

5. Actual browser spend → server → database → reload recovery returns one receipt/roll without reroll.
