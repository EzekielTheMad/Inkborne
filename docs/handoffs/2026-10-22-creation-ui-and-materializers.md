## Delivered and checked

The creation interface is behind server-only `INKBORNE_CLASS_ORIGIN_CREATION_UI`,
which defaults off and accepts only literal `true`. It persists the complete
immutable account-scoped original intent before sending. Reload, explicit check
and retry retain its operation ID; uncertain, absent or mismatched responses
cannot clear it or invoke legacy creation. Confirmed sign-out/account transition
invalidates old callbacks and writes. A failed sign-out attempt retains the
original. Malformed or unavailable storage blocks new requests.

Both actions bind the page account as a consistency constraint. The production
adapter derives authority once from the same-token verifier and rejects a
different current account before creating a service client or calling RPC.
Recovery compares the entire original canonical intent. Only confirmed account,
operation and character IDs reach the interface. Selecting the new path also
refuses an old tab's legacy create action. No flag was enabled.

B2 consumes the sealed current-transaction B1 plan and corresponding journal.
Real original controller AFTER triggers insert all planned active/dormant grants
with native IDs/times and exact returned-row equality. Active projections require
the actual choices update and rebound order first. Recursive derived refs are
checked no-ops. The protected branch does not delete, upsert, allocate again or
rerun untouched empty-history planning after writes. Five original function
bodies have finite branches; eight remain byte-identical. Existing legacy API
ACLs, owners, global Auth denials, both gates and all13 readiness flags remain.

The class-owned journal reader adds only postgres as a nonowner EXECUTE caller;
B2 adds no explicit postgres table/column grant on original private history.
Native postgres already inherits administrative reads; this is not effective
administrator isolation or the reader's exclusive possible access path.
B2 does not perform the B3
choices update, private proof consumption, semantic order write or finalization.
Its fixture injects prior history/pending proofs and manually prepares choices;
these are explicitly synthetic, not authenticated class-save acceptance.
